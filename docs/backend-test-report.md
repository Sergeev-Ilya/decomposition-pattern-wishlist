Добавлены пять тестов auth и пять wishlist; gateway suite из 61 теста уже закрывал требуемые границы доверия и отказы и оставлен без искусственного расширения.

Service integration tests используют отдельные настоящие PostgreSQL: `127.0.0.1:55432/wishlist_auth_test` и `127.0.0.1:55433/wishlist_data_test`. `DATABASE_URL` игнорируется. Явный `TEST_DATABASE_URL` также обязан указывать БД с именем `*_test`. Cleanup удаляет только пользователей/списки с ID, созданными соответствующим запуском; `TRUNCATE` не используется. Продуктовые БД и volumes не очищались, секреты конфигурации не менялись.

## Исправления

1. **Auth: bodyless logout.** Для настоящего HTTP POST с `Content-Type: application/json`, без `Content-Length` и без `Transfer-Encoding`, `req.is()` возвращал `null`, и допустимый контрактом `/auth/logout` отвечал 415. Guard теперь проверяет значение заголовка независимо от наличия тела, сохраняя требование `application/json` и поддержку `charset`. Добавлена регрессия с raw HTTP: до исправления 415, после — 204 с удалением cookie. Browser gateway по-прежнему требует `{}` для этой операции.
2. **Безопасность тестовой инфраструктуры auth.** Прежний guard проверял суффикс `_test` только для значения по умолчанию, разрешая произвольный explicit `TEST_DATABASE_URL`. Теперь проверяется любое значение, как в wishlist setup.

Из продуктового кода изменен только `backend/auth-service/src/app.ts`. Сервис успешно собран локально и пересобран/обновлен в Compose; остальные образы не пересобирались.

## Подтвержденное покрытие

### Auth

- Нормализация email, уникальность и конкурентная регистрация: один пользователь и одна сессия на три одновременные попытки, остальные 409 без cookie.
- Атомарность регистрации: реальная транзакция PostgreSQL и INSERT пользователя, затем внедренный отказ INSERT первой сессии; ответ 503, cookie отсутствует, пользователь откачен. Остальная работа БД настоящая.
- Пароль сохраняет крайние пробелы, длина считается в Unicode code points; используется scrypt. Неизвестный email и неправильный пароль дают одинаковую ошибку.
- JWT проверен настоящей подписью HS256; отклонены другой ключ, HS384, `none`, неправильные issuer/audience, массив audience, отсутствующие обязательные claims, неверные UUID, неизвестные sid/sub, будущий iat, неверный TTL и истекший JWT. Проверена привязка timestamps к строке БД.
- Чужой sub с действительным чужим sid не авторизует запрос и не отзывает исходную сессию. Logout немедленно отзывает текущую сессию, сохраняет независимую login-сессию и идемпотентен.
- При отказе БД logout действующей cookie дает 503 без `Set-Cookie`; health также сообщает 503. Отсутствующая/невалидная cookie безопасно очищается.
- JWT/хеш пароля/служебный session ID не выдаются в публичном auth JSON; cookie имеет HttpOnly, SameSite=Lax, Path=/ и срок 24 часа.

### Wishlist

- Внутренний credential проверяется до доверия UUID. Чужой владелец получает 404 на чтении и всех мутациях, включая подарки и ротацию ссылки. Gift ID другого списка не позволяет обойти границы агрегата.
- После брони обе проекции владельца не содержат полей бронирования. Публичные данные не содержат ownerId/email/секретов; гость видит `reserved`. Авторизованный владелец не может бронировать собственный подарок.
- Цены 0 и 9007199254740991 передаются точно; отклонены отрицательные, дробные, небезопасные числа, строки, null и отсутствие обязательной цены. Опциональные URL/заметка имеют пустые defaults; разрешены HTTP/HTTPS и пустой URL, запрещены credentials, относительные, javascript/FTP URL и null. Проверены длины, неизвестные поля и пустой PATCH.
- Из восьми одновременных броней одна успешна, семь получают 409. В PostgreSQL хранится только SHA-256 от UTF-8 секрета.
- Из пяти конкурентных добавлений при 99 подарках проходит одно, итоговый размер ровно 100.
- Две детерминированные гонки с реальным PostgreSQL lock contention: ротация и удаление ставятся в очередь раньше устаревшей брони. После снятия блокировки мутация проходит, бронь получает 404, строки бронирования не создаются. Ожидание блокировок подтверждается через `pg_stat_activity`, произвольная задержка не задает порядок гонки.
- PATCH сохраняет активную бронь, увеличивает version и включает `giftChanged`. Ротация закрывает старую общую ссылку и сохраняет секретный доступ.
- Повторная отмена сохраняет `canceledAt`; новая бронь получает другой секрет, старый секрет ее не отменяет.
- Каскады удаления списка и отдельного забронированного подарка делают секреты недоступными. Удаление одного подарка сохраняет другой подарок и список.

### Gateway

61 существующий тест подтверждает allowlist маршрутов/методов, нейтральные 404, 405+Allow, запрет internal маршрутов, удаление поддельных identity/internal/forwarded заголовков, отсутствие доверия Bearer и отсутствие кеширования auth. Проверены точные Origin и X-Requested-With, Content-Type, обязательный объект JSON, `{}` для пустых операций/DELETE и предел 32 KiB. Некорректная или невалидная присутствующая cookie на optional маршруте дает 401, отказ auth не превращает запрос в гостевой. Secret GET/cancel не обращаются к auth и не передают cookie. Проверены очистка служебных полей auth JSON, allowlist ответных заголовков, безопасные ошибки без upstream подробностей, 503/504, отдельные rate limits и `Retry-After`.

## Живой сценарий через localhost:8880/api

Повторяемая проверка сохранена в `backend/tests/api-smoke.mjs`. Использованы настоящие gateway, auth, wishlist и PostgreSQL Compose; frontend UI не тестировался. Unsafe запросы отправляли точный Origin, `X-Requested-With: Wishlist`, `application/json` и `{}` для операций без полей/DELETE. Вывод содержит только названия шагов, статусы и итог assertions, без паролей, cookie и токенов.

Успешно выполнены: регистрация уникального синтетического аккаунта с cookie → создание списка и подарка → гостевая бронь → owner/guest privacy → запрет собственной брони → изменение забронированного подарка и `giftChanged` → ротация общей ссылки → 404 старой ссылки и сохранность секрета → отмена/повтор → новая бронь → повтор старого секрета без влияния на новую бронь → DELETE списка → 404 обеих секретных ссылок и общей ссылки → logout → немедленный 401 старой cookie.

При временно остановленном **auth-service**:

| Запрос через gateway | Результат |
|---|---:|
| Secret GET с действующей session cookie | 200 |
| Secret cancel с malformed session cookie | 200 |
| Anonymous public GET | 200 |
| Owner GET с cookie | 503 |
| Optional-cookie public GET | 503 |
| Logout с cookie | 503, без Set-Cookie |
| Тот же `/auth/me` после восстановления auth | 200 |

Auth запущен обратно и дождался Docker health=healthy. Та же сессия сохранилась после рестарта. Созданный список удален, подарки и обе брони удалены каскадно. Синтетический auth-аккаунт остается в локальной БД, поскольку удаления аккаунта в API MVP нет; его сессия отозвана. Прямых запросов к продуктовым БД smoke не делает.

## Фактически выполненные команды

Из корня репозитория либо указанной рабочей директории:

```sh
# cwd: backend/auth-service
npm test
npm run build

# cwd: backend/wishlist-service
npm test

# cwd: backend/api-gateway
npm test

# cwd: backend
docker compose config --quiet
docker compose up -d --build auth-service

# cwd: repository root
node --check backend/tests/api-smoke.mjs
node backend/tests/api-smoke.mjs --with-auth-outage

# cwd: backend; stop/start/inspect выполнены самим smoke с finally-восстановлением
docker compose stop auth-service
docker compose start auth-service
docker compose ps
```

Итоговый `docker compose ps`: auth-db, wishlist-db, auth-service, wishlist-service, api-gateway и frontend — **6/6 healthy**. API доступен через согласованный loopback порт 8880; это не подтверждение готовности frontend или завершенного deploy-gate.

Неуспешных прогонов с последующим исправлением: **2**, без учета sandbox отказов. Первый выявил ошибку нового JWT fixture: jsonwebtoken автоматически добавлял удаленный iat; исправлено `noTimestamp`. Второй воспроизвел продуктовый баг bodyless logout; выполнено одно исправление продуктового кода. После этого auth suite прошел. Wishlist и gateway suite прошли без итераций исправления. Отказы sandbox при доступе к Docker/localhost повторены с escalation; они не являются функциональными дефектами.

Нагрузочное тестирование и p95 не выполнялись. Указанные гонки проверяют инварианты конкурентных транзакций, а не производительность под нагрузкой. Блокеров backend gate не обнаружено. `.project/state.json` не изменялся.

# Wishlist — выбор технологического стека

Статус: **рекомендуемый вариант выбран по поручению пользователя 2026-10-28**: «Выбери рекоммендуемый стек». Основание — согласованные [требования](requirements.md). Следующий этап — спецификация страниц.

## Рекомендуемый вариант — React + Express

| Слой | Выбор | Причина для Wishlist |
|-------|-------|----------------------|
| Интерфейс | React + Vite + TypeScript + Tailwind CSS | Соответствует `templates/prototype/`; подходит для адаптивных форм, личного кабинета и гостевого просмотра списка. |
| Среда выполнения | Node.js 24 LTS | Поддерживаемая ветка вместо Node.js 20 из шаблона. Единая среда для API, gateway и сборки интерфейса. |
| Backend | Express 5 + TypeScript | Близок к шаблону сервиса; явные обработчики прав владельца, гостевой брони и отмены. |
| Хранилище | PostgreSQL 18 + SQL-миграции + драйвер `pg` | Постоянное хранение, транзакции и уникальное ограничение на активную бронь подарка; цена хранится точно, без двоичной арифметики. |
| Авторизация владельца | JWT в HttpOnly cookie + серверный учет сессий | Поддерживает email/пароль и реальное прекращение текущей сессии при выходе. |
| Контракты | REST + OpenAPI 3.1 | Отдельные контракты управления владельца и гостевого доступа, включая конфликт бронирования. |
| Единая точка API | Express API Gateway / BFF | Интерфейс обращается к `/api`; внутреннее разбиение сервисов определяется на этапе архитектуры. |
| Backend-проверки | Vitest + supertest; интеграционные проверки на PostgreSQL | Проверка прав доступа, отмены, сохранности данных и конкурентного бронирования. |
| Frontend-проверки | Vitest + Testing Library + Playwright | Проверка форм и полных сценариев владельца и гостя на телефоне и компьютере. |
| Запуск | Docker Compose | Воспроизводимый запуск приложения и БД с постоянными томами. Целевое окружение согласуется после прототипа. |

На дату проверки Node.js 24 имеет статус LTS, Node.js 20 — EOL: [официальный список выпусков](https://nodejs.org/en/about/previous-releases). PostgreSQL 18 поддерживается до ноября 2030 года: [политика версий](https://www.postgresql.org/support/versioning/). Vite предоставляет React/TypeScript-пресет; Node.js 24 соответствует указанным требованиям среды: [руководство Vite](https://vite.dev/guide/).

Это рекомендуемый вариант по скорости получения MVP и совпадению с шаблонами репозитория. При ориентире 1 000 аккаунтов и 50 одновременных посетителей усложнять инфраструктуру заранее не предлагается. Фактические показатели времени ответа проверяются на выбранном окружении, а не гарантируются названием стека.

## Альтернатива A — Next.js + Express

Интерфейс: Next.js + React + TypeScript + Tailwind CSS. Backend: тот же Node.js 24 + Express 5; PostgreSQL, REST/OpenAPI, авторизация и проверки сохраняются. Слой Next.js может выполнять роль BFF; второй дублирующий gateway не нужен.

- Подходит, если позднее понадобится серверный рендеринг публичных страниц или команда уже хорошо знакома с Next.js.
- Для текущего MVP серверный рендеринг не требуется: основные экраны — формы и кабинет, общие списки не должны индексироваться. Это оценка требований проекта.
- Потребуется перенести Vite-прототип и определить границу между Next.js и отдельным API; это увеличивает объем начальной настройки относительно рекомендуемого варианта.

## Альтернатива B — React + Fastify

Интерфейс остается React + Vite + TypeScript + Tailwind CSS. Backend: Node.js 24 + Fastify; PostgreSQL, REST/OpenAPI, JWT, Docker Compose и браузерные проверки сохраняются. Gateway также можно реализовать на Fastify.

- Подходит, если команда предпочитает схему валидации и плагинную организацию Fastify.
- Требует адаптации Express-шаблонов, middleware и API-тестов. Для HTTP-проверок можно использовать Fastify `inject`; конкурентность все равно проверяется с настоящей БД.
- Для заявленной нагрузки выигрыш относительно Express заранее не измерен; выбирать этот вариант только ради предполагаемой скорости не предлагается.

## Сравнение

Оценки относительные, применительно к этому репозиторию; сроки в днях и опыт команды пока неизвестны.

| Критерий | React + Express | Next.js + Express | React + Fastify |
|----------|-----------------|-------------------|-----------------|
| Начальная сложность | Наименьшая: близок к шаблонам | Выше: перенос прототипа и граница BFF/API | Умеренная: адаптация серверного шаблона |
| Скорость получения MVP | Предпочтительный вариант | Дополнительная настройка без обязательной функции MVP | Дополнительная адаптация без обязательной функции MVP |
| Масштабирование | Проверять нагрузкой; возможны реплики API с общей БД | Возможны реплики API; добавляется серверный слой интерфейса | Проверять нагрузкой; возможны реплики API с общей БД |
| Знакомство команды | Неизвестно | Неизвестно | Неизвестно |
| Совпадение с репозиторием | Наибольшее, с обновлением runtime и Express | Частичное: новый frontend/BFF | Частичное: новый backend/gateway |

## Общие условия реализации

- Бронирование должно быть атомарным на уровне PostgreSQL. Уникальное ограничение, транзакция и обработка конфликта обеспечивают одну активную бронь; проверка «свободен ли подарок» только в приложении недостаточна. Граница сервиса и схема таблиц определяются архитектурой и API-дизайном.
- Цена передается в согласованном десятичном формате, хранится как точное значение — например, целое число копеек или `NUMERIC`. Вариант фиксируется в схеме БД; для интерфейса по требованиям используется RUB по умолчанию.
- Cookie авторизации: HttpOnly, Secure в удаленном окружении, подходящий SameSite; изменение данных защищается от CSRF. Пароли хранятся стойкими хешами. Секреты не хранятся в `localStorage` и не пишутся в журналы.
- JWT сам по себе не обеспечивает немедленный выход. Нужен серверный учет сессии с проверкой ее действительности на защищенных запросах; logout отзывает текущую сессию и удаляет cookie. Сроки токенов и обновление фиксируются в архитектуре.
- Секрет гостевой отмены независим от JWT и общей ссылки списка, хранится в защищенном представлении и дает доступ только к своей брони. Отзыв общей ссылки не лишает дарителя возможности отмены.
- Скрытие броней от владельца проверяется в ответах API управления, а не только в интерфейсе. Ограничение анонимного просмотра сохраняется согласно требованиям.
- Redis, брокер сообщений, S3, почтовый сервис и внешняя система авторизации для согласованного MVP не предлагаются. Число сервисов и границы данных определяются позже.

## Совместимость с шаблонами

В `templates/backend/service/` сейчас указаны Docker-образ Node.js 20, Express 4 и типы `@types/express` 5. При создании продуктового кода нужно согласовать Docker-образ, `engines`, runtime Express и его типы с выбранным стеком. Express 5 имеет несовместимые изменения с Express 4: [официальное руководство миграции](https://expressjs.com/en/guide/migrating-5/). Шаблоны на этом этапе не изменяются.

Версии React, Vite, Tailwind и проверочных инструментов не следует слепо копировать из старого шаблона: совместимые поддерживаемые версии и lockfile фиксируются при реализации, затем проверяются сборкой и соответствующими тестами.

## Решение

**Выбран рекомендуемый вариант по поручению пользователя 2026-10-28:** React + Vite + TypeScript + Tailwind CSS, Node.js 24 LTS + Express 5, PostgreSQL 18, REST/OpenAPI 3.1 и Docker Compose. Авторизация — JWT в HttpOnly cookie с серверным учетом сессий; проверки — Vitest, supertest, Testing Library и Playwright. Альтернативы выше сохранены как обоснование выбора. Стек утвержден, повторное согласование не требуется.
